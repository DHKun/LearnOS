# LearnOS 课程制作

这份 skill 凝练自 `http-hands-on` 的重做过程。旧课的问题不是文字错，而是**交互没有起到教学作用**：实验照题干点一下就过、开关拨了没效果、动画只是依次高亮方框。下面的原则和流程都是为了避免这些问题。

做课前先读 `content/courses/http-hands-on/README.md`，它是按本 skill 做出来的完整样例，后文多处引用它的文件。

## 1. 开工前：确认平台约束

1. **这是新课还是改已有的课？** 课程一旦有学习记录，必修章节、Block、完成规则、`validators.ts` 的哈希和题库都会冻结。结构性改动要发布**新 slug**；只改文案、可选动画、不影响完成条件的可选 Block 可以原地改。详见 `references/platform-contract.md` 的“冻结规则”。
2. **判分规则写在哪里？** 冻结检查只哈希 `validators.ts` 本身，不包含它导入的模块。判分规则通常放在 `simulation/*.ts` 里，修改它们不会触发冻结检查，但同样会让已有学员的通过状态和新规则不一致，所以要当作结构性变更对待。
3. 读 `docs/MVP-SPEC.md` 与 `AGENTS.md` 的相关约束：答案只在服务端、不得 eval 或执行用户代码、不用 iframe、不引入容器靶场。这决定了实验只能是**确定性的纯 JS 模拟**。

## 2. 教学设计：先定这五件事

先写一张章节表交给用户确认，再写代码。表里每章要有：要解决的问题、概念动画、实验工单、完成条件。

### 2.1 一个世界，一个比喻

为整门课设计**一个**模拟对象（HTTP 课是网站 `library.test`，编码课可以是一台“只认 0 和 1 的打字机”），所有实验都在它上面做，前面章节学到的规则在后面继续生效。比喻也只用一个，贯穿全课。每章换一个玩具、换一个比喻，学生就得反复重建心智模型。

### 2.2 实验先给症状，再让学生修

每个实验都以**工单**开头：一个已经坏掉的请求、配置或数据，加上一个可验证的目标。学生要观察、推理、修改，而不是照着说明填空。

自检，任一条不满足就重新设计：

- **初始状态不能就是答案**，也不能离答案只差一个字符。（旧课的综合任务一，默认值就是正确答案。）
- **每个可调的控件都必须改变可观察的结果**。没有效果的开关要么删掉，要么补一个能体现它的场景。（旧课的 SameSite 开关在只有同站请求的场景里毫无作用。）
- **题干不说出答案**。写“让这五个场景全部变绿”，而不是“请勾选 Secure、HttpOnly 和 SameSite=Lax”。
- **正确答案应当需要推理才能得到**：比如要对照两条记录、权衡两个目标（Strict 太严、None 太松），或者要先查一步再做一步。
- **失败的反馈指向原因，不泄露答案**：“PUT 会用你发送的内容整体替换资源”，而不是“请改用 PATCH”。

常见的实验类型、各自的状态结构和判分方式见 `references/lab-patterns.md`。

### 2.3 服务端按结果判分

校验器重新计算学生做出的结果，而不是比对固定答案。多步操作类的实验提交**完整的操作记录**，服务端在一个全新的模拟世界里从头重放、检查最终状态。这样“先做错再修好”也能通过，而伪造的 `passed` 字段无效。

### 2.4 动画展示状态变化

每一步都要看到**某个东西变了**：数据包在节点之间移动、表里多了一行、缓存条目过期。只是依次高亮方框的“动画”不算。能切换条件对比的（POST 和 PUT 重试、HTTP 和 HTTPS）就加 `controls`。基础组件在 `components/education/scene-kit.tsx`，写法见 `references/lab-patterns.md` 的“概念动画”一节。

### 2.5 文字短，穿插小测

- 每章围绕一个具体问题开场；正文以短段落为主，表格只用于真正需要对照的内容。
- 少用“通常”“可能”“取决于部署”之类的保留性措辞。严谨的细节可以写一句，或放进后面的章节。
- 每章穿插 1～2 个不计分的 `MiniCheck`；需要计入完成条件的检查才用服务端 `KnowledgeCheck`。
- 题目以情景判断为主（“看到这个响应，下一步该查什么”），少考定义背诵。

## 3. 制作流程

按顺序做，每一步都有可执行的检查。

1. **章节表**（见 2），先给用户确认。
2. **模拟引擎**：`simulation/` 下写纯函数，不做任何网络 I/O、不依赖 DOM，前端和校验器共用。输入一律严格解析，并设长度和数量上限。
3. **判分规则**：每个实验一个 `gradeXxx()`，同样放在 `simulation/`；`validators.ts` 只负责严格解析输入，再调用判分规则。
4. **单元测试先行**：`tests/unit/<slug>.test.ts`。每个校验器至少覆盖三种情况：初始状态或照抄题干时不通过、正确做法通过、伪造的 `passed` 等字段被忽略。模板见 `references/verification.md`。
5. **组件**：实验外壳用 `components/education/lab-kit.tsx`（`Ticket`、`LabFooter`、`useLabSubmit`、`Verdict`），状态用 `useActivityState` 持久化，`normalize` 函数要能容忍任意输入。只属于这门课的组件留在课程目录里。
6. **MDX 与题库**：写法和坑见 `references/platform-contract.md`。
7. **`pnpm courses:validate`**，然后 `pnpm typecheck` 和 `pnpm lint`。
8. **E2E 全课走通**：`tests/e2e/<slug>.spec.ts` 通过真实界面完成每一章，最后核对结课状态和积分（章节数 × 10 + 结业 50）。
9. **截图人工检查**：用 `scripts/review-shots.ts` 截出每章在 1440px 和 390px、亮色和暗色下的样子，逐张看。清单见 `references/verification.md`。很多问题测试发现不了，只有看图才能发现。
10. **文档**：课程目录下的 `README.md`（设计思路、章节表、判分说明）、`docs/decisions.md` 的决策记录、`PLAN.md`。

## 4. 已知的坑

这些都实际踩过，靠原则推不出来，所以单独列出：

- **“拒收”导致的虚假通过**：配置非法、什么都没生效时，那些“不应该发生某事”的场景会显得安全、显示绿色。这种情况下要把所有场景都判为不通过。
- **提示语重复**：同一条错误既显示在结果面板里，又出现在判定提示里。
- **把线索喂给学生**：诊断类实验里，不要在出错的记录里直接附上答案线索；线索应放在另一条记录里，让学生自己去对照。
- **prose 样式**：课程组件渲染在 MDX 的 prose 容器里，`<ul>` 会自动带圆点，需要加 `m-0 list-none p-0`。
- **窄屏下的三栏动画**：“节点—通道—节点”在 390px 下要改为纵向堆叠（`grid-cols-1 sm:grid-cols-[…]`）。
- **硬编码颜色**：旧课的 SVG 写死了浅色值，暗色模式下非常刺眼。一律使用主题 token（`bg-primary/10`、`text-success`、`border-border` 等）。
- **E2E 定位**：给 select 和 input 加 `aria-label`；用 `getByText` 时注意折叠表格里的隐藏文本，必要时限定在实验的 `data-testid` 范围内，或加 `exact: true`。
- **学习页目录默认只展开当前单元**：E2E 要跨单元点击章节时，先点开对应单元，或直接用 `?lesson=<id>` 跳转。
