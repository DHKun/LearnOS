## 从回车到看到网页：不止一次 HTTP

URL 已经认识了，但浏览器如何真正找到服务器？以 `https://example.test/guide` 为例，我们把过程分成几个层次。

1. **解析 URL**：识别 HTTPS 方案、主机与路径。
2. **定位目标**：可能通过 DNS 查询获得地址，也可能使用已有缓存。
3. **建立可用连接**：现代 HTTPS 可能使用 TCP + TLS 或 QUIC + TLS，具体取决于 HTTP 版本和协商结果。
4. **发出 HTTP 请求**：例如请求 `/guide`。
5. **接收并处理响应**：浏览器可能继续解析 HTML、执行脚本、请求图片。

## HTTP 和其他协议的分工

| 相关技术 | 解决的问题 | 与 HTTP 的关系 |
| --- | --- | --- |
| DNS | 把域名解析成可连接的地址 | 访问前常见的定位步骤，不属于 HTTP 消息本身 |
| TCP | 提供可靠有序的字节流 | HTTP/1.1、HTTP/2 常使用 |
| QUIC | 基于 UDP 的安全多路传输 | HTTP/3 使用 |
| TLS | 提供传输机密性、完整性与服务器身份认证 | HTTPS 中保护 HTTP 交换 |
| HTTP | 规定请求、响应和资源交互语义 | 无论 HTTP/1.1、2 或 3，语义大体一致 |

<Callout type="tip" title="学习本课的边界">
后面的模拟器采用便于阅读的 HTTP/1.1 报文形式，用来学习协议语义；它不是抓取真实 TCP 包，也不是 HTTP/2 或 HTTP/3 在网络上的二进制格式。
</Callout>

## 为什么一个网页可能同时发出很多请求？

HTML 可能引用 CSS、图片、字体、JavaScript，脚本还可能再请求 API。假设网页至少需要下面这些资源：

```text
GET /index.html      → 200 text/html
GET /app.css         → 200 text/css
GET /logo.svg        → 200 image/svg+xml
GET /api/profile     → 401 application/json
```

即使主页显示出来了，`/api/profile` 仍然可能因为未登录而失败。这也是为什么“网页能打开”不等于“所有请求都成功”。
