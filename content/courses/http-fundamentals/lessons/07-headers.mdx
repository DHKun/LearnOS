## Header 是描述这条消息的附加信息

请求行和状态行都很简短，实际 Web 通信还需要表达数据格式、缓存规则、认证条件等。Header 以名称和值组成字段，例如：

```http
Accept: application/json
Content-Type: application/json
Cache-Control: no-store
Authorization: Bearer example-token
```

这个例子中的 `example-token` 只是教学占位符，不能拿来访问任何真实服务。

## Accept 与 Content-Type 的区别

它们名字容易记混，但回答的是两个问题：

| Header | 关注的问题 | 场景 |
| --- | --- | --- |
| `Accept`（请求头） | “我愿意接收什么格式的响应？” | 客户端偏好 JSON |
| `Content-Type`（请求或响应头） | “当前这条消息的表示内容是什么格式？” | 请求 Body 是 JSON，或响应 Body 是 HTML |

例如：客户端提交 JSON 便签，服务器也返回 JSON：

```http
POST /api/notes HTTP/1.1
Host: api.example.test
Accept: application/json
Content-Type: application/json

{"title":"HTTP 学习笔记"}
```

`Accept` 不会自动把请求 Body 转成 JSON；`Content-Type` 也不等于服务器一定愿意接收这种格式。后面会用模拟器看到 `415 Unsupported Media Type`。

## 其他常见字段

- `Host`：HTTP/1.1 的目标主机信息。
- `Location`：某些重定向响应、创建资源响应中指向相关 URI。
- `Cache-Control`：告诉缓存如何处理表示。
- `ETag`：为某个表示提供验证标识，可用于条件请求。
- `Cookie`：客户端向服务端发送适用的 Cookie。
- `Set-Cookie`：服务器要求客户端保存或更新 Cookie。

<Callout type="tip" title="Header 不是随便写几个字就能生效">
字段名称有标准语义，但某个 API 是否支持、如何响应，仍由服务器实现决定。课程实验会明确说明哪些行为是预先设定的模拟规则。
</Callout>
