## 排错第一步：找到失败的那条请求

「页面坏了」太笼统。打开 Network 面板，先找出出错的是哪一条请求，再按下面的顺序看：

1. **有没有状态码？** 状态栏显示 `(failed)`，说明根本没有 HTTP 响应：可能是域名写错（DNS）、连不上、证书问题，或被浏览器的安全策略拦下。这时去看错误名称，例如 `ERR_NAME_NOT_RESOLVED`。
2. **状态码属于哪个家族？** 4xx 看请求，5xx 找后端。
3. **请求是不是你以为的样子？** 对比地址、方法、`Content-Type`、`Accept`，以及最常被忽略的一点：**`Cookie` 到底有没有带上**。
4. **读响应正文。** 错误信息、错误码、requestId 往往就在里面。
5. **分清有关和无关。** `favicon.ico` 返回 404 不影响功能；`304` 是缓存在正常工作，不是错误。

| 看到 | 先检查 |
| --- | --- |
| `(failed)` | 域名、端口、网络、证书 |
| 401 | 请求里有没有凭据；Cookie 的 Path、SameSite、是否过期 |
| 403 | 当前账号的权限 |
| 404 | 地址是否符合 API 约定 |
| 405 | 方法是否被支持（看 `Allow`） |
| 415 / 400 | `Content-Type` 与正文格式 |
| 500 / 503 | 服务端日志；带上 requestId 去问后端 |

## 在真实浏览器里怎么做

真实的 Network 面板比这里的模拟多一些实用功能：

- **Preserve log（保留日志）**：页面跳转后不清空记录，排查重定向和登录流程时很有用；
- **Disable cache（停用缓存）**：排除缓存干扰；
- **筛选 Fetch/XHR**：只看脚本发出的 API 请求；
- 点开一条请求，在 **Headers / Payload / Response / Timing** 标签之间切换；
- 右键 **Copy → Copy as cURL**，可以在终端里原样重放这个请求。

<Callout type="warning" title="分享之前先脱敏">
复制的 cURL 命令和导出的 HAR 文件里含有 Cookie、Authorization 等凭据。发给别人之前，先删掉这些值。
</Callout>
