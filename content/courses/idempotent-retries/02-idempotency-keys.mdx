幂等键（idempotency key）是**客户端为一次业务操作生成的唯一标识**。同一个操作的所有重试都携带同一个键，服务端据此识别重复。

```http
POST /payments
Idempotency-Key: 6f1c2a2e-9b1f-4e2a-8f3d-2b7c9a1e4d55

{"orderId":"42","amount":99}
```

注意两个细节：

- 键属于「一次业务操作」，不是「一次 HTTP 请求」。
- 键必须由客户端生成并在重试时复用；如果每次重试都换新键，去重就失效了。

<Callout type="warning" title="最常见的错误">
在「发送请求」的函数里生成 UUID。这样每次重试都会得到新键，服务端看到的是 N 个不同的操作。正确做法是在「用户点击支付」时生成，把键和操作一起写入本地状态。
</Callout>

## 服务端流程

一个可靠的幂等处理分四步：

```text
1. 校验键格式与请求体
2. 用键占位（INSERT ... ON CONFLICT DO NOTHING）
   - 插入成功：本次请求成为执行者
   - 冲突：已有请求在处理或已完成
3. 执行副作用，并在同一事务中写入结果
4. 重复请求直接返回已存结果（不能重新执行）
```

关键点是 **占位与副作用在同一事务语义下完成**。如果先查再写，两个并发请求会同时查到「不存在」然后都执行。

数据库层面通常这样实现：

```sql
CREATE TABLE idempotency_keys (
  key          text PRIMARY KEY,
  request_hash text NOT NULL,
  status       text NOT NULL,      -- processing | completed | failed
  response     jsonb,
  created_at   timestamptz NOT NULL DEFAULT now()
);

INSERT INTO idempotency_keys (key, request_hash, status)
VALUES ($1, $2, 'processing')
ON CONFLICT (key) DO NOTHING
RETURNING key;
```

如果 `RETURNING` 没有返回行，说明键已存在：读取已有记录，若 `completed` 则直接返回缓存的响应；若 `processing` 则返回 409 或让客户端稍后重试。

## 请求指纹

只比较键还不够。恶意或错误客户端可能用同一个键发送不同请求体。服务端应保存 **请求体哈希**，键相同但哈希不同时返回 `422`，而不是把旧结果套用到新请求上。

<Callout type="tip" title="幂等键不是授权">
键只用于去重，不证明调用者有权执行该操作。身份、权限和资源归属仍然要独立校验。
</Callout>

## 去重记录要保留多久

幂等记录不能永久保存，也不能太短：

- 太短：客户端在网络恢复后重试，去重记录已过期，重复执行。
- 太长：存储增长，且可能把「用户真的想再付一次」误判为重复。

常见做法是按业务风险设置 TTL（例如 24 小时），并让客户端为新的业务操作生成新键。

## 失败与重试

执行失败时，不要立刻删除键：

- 若失败是确定性业务错误（余额不足），可以记录 `failed` 并允许同键重试返回同一错误。
- 若失败是暂时性错误（数据库超时），应记录可重试状态，并保证重试时不会重复产生副作用。

一个实用原则：**副作用要么和键记录在同一事务提交，要么通过可补偿的步骤保证最终只生效一次。**

## 对照：三种常见策略

| 策略 | 重复请求结果 | 问题 |
| --- | --- | --- |
| 无键、无去重 | 每次执行 | 重复扣款 |
| 随机键（每次请求新键） | 每次执行 | 看似有键，实际无效 |
| 业务操作稳定键 + 服务端去重 | 返回首次结果 | 需要存储与 TTL 管理 |

## 本文小结

- 幂等键标识「一次业务操作」，重试必须复用同一个键。
- 服务端用唯一约束占位，重复请求直接返回已存结果。
- 保存请求哈希，防止同键不同体。
- 键不是授权，权限仍需独立校验。
