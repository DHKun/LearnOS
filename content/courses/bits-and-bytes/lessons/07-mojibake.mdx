## 乱码不是“坏了”，是“读错了”

打开一个文件，看到“浣犲ソ”“锟斤拷”“cafÃ©”……很多人第一反应是文件坏了。其实大部分乱码里，字节一个都没少，只是**用错了密码本**。

## 常见乱码的“指纹”

不同的错法会留下不同的样子，认识它们就能很快判断原因：

| 看到的样子 | 原因 | 字节还在吗 |
| --- | --- | --- |
| 一串生僻汉字，如“浣犲ソ” | UTF-8 的字节被当成 GBK 读 | 在，换成 UTF-8 读即可 |
| 带 `Ã`、`Â`、`ä` 的字母，如“cafÃ©” | UTF-8 的字节被当成 Latin-1 读 | 在 |
| 一串 `�` | 字节不是合法的 UTF-8，比如 GBK 的字节被当成 UTF-8 读 | 原文件里在，但被“另存为”后就没了 |
| “锟斤拷” | 原文已经被替换成 `�`（UTF-8 字节 `EF BF BD`），这些字节又被当成 GBK 显示 | 不在了 |
| 一串 `?` | 转换成不支持中文的编码时，汉字被换成了问号（`3F`） | 不在了 |
| 最后一个字变成 `�` | 按字节截断，切坏了最后一个字符 | 缺的那几个字节不在了 |

判断“能不能恢复”只有一条标准：**原来的字节还在不在**。

## 怎么避免

- 文件、网页、数据库、接口**统一用 UTF-8**；
- 无法统一时，在交接的地方**明确声明编码**，比如 HTTP 的 `Content-Type: text/html; charset=utf-8`；
- 发现乱码时，**先别保存**。一旦按错误的编码另存，`�` 和 `?` 就成了真正的数据。
