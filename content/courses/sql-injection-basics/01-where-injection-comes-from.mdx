一个最普通的登录接口，可能长这样：

```ts
const sql = `SELECT id, password_hash FROM users WHERE email = '${email}'`;
const rows = await db.query(sql);
```

开发者期待用户输入类似 `alice@example.com` 的邮箱。但输入框并不受期待约束。攻击者可以输入：

```text
' OR '1'='1' --
```

拼接后的 SQL 变成：

```sql
SELECT id, password_hash FROM users WHERE email = '' OR '1'='1' --'
```

`--` 把后面的引号和条件全部注释掉。`OR '1'='1'` 永远为真，查询返回users表里的第一行，登录逻辑如果只看「有没有查到用户」，就会被绕过。

<Callout type="warning" title="问题不在引号，在结构">
注入的本质不是「输入里有特殊字符」，而是**数据被当成了语法**。当用户输入可以改变 SQL 的解析结构时，任何补丁都只是让攻击者换一种写法。
</Callout>

## 信任边界在哪里

把系统拆成三层看：

| 层 | 可信程度 | 正确做法 |
| --- | --- | --- |
| 代码里的 SQL 模板 | 可信 | 固定结构，不拼接用户输入 |
| 用户输入的邮箱、密码 | 不可信 | 永远作为「值」传递 |
| 用户输入的表名、排序字段 | 不可信 | 只允许白名单枚举 |

大多数注入发生在第二、三层混淆的时候：开发者把用户输入当成 SQL 片段，而不是值。

## 转义为什么总是慢一步

「把单引号替换成两个单引号」看起来能挡住上面的例子。它确实能挡住一部分攻击，但它的安全性依赖四个前提：

1. 数据库的转义规则没有例外（不同数据库、不同字符集并不一致）。
2. 每一个进入 SQL 的字符串都真的被转义了（漏一处就前功尽弃）。
3. 数值上下文也被正确处理（`WHERE id = ${id}` 根本没有引号可转义）。
4. 代码里没有人后来加了一句新的拼接。

只要有一条不成立，注入就回来了。更重要的是，**转义是「过滤坏字符」，而注入是「结构被改变」**。用过滤去解决结构问题，本质上是在黑名单里追着攻击者跑。

## 一个更隐蔽的例子

```ts
const orderBy = req.query.sort ?? "created_at";
const sql = `SELECT * FROM orders ORDER BY ${orderBy}`;
```

这里没有引号，也没有字符串值。`sort=created_at; DROP TABLE orders--` 在某些允许一次执行多条语句的驱动配置下会直接造成破坏，甚至没有破坏性语句时也能通过 `CASE WHEN` 做布尔盲注。

<Callout type="tip" title="判断口诀">
问自己一句：**这段用户输入，最终是作为一个「值」出现在 SQL 里，还是作为 SQL 文本的一部分？** 只要答案是后者，它就是注入面。
</Callout>

## 本文小结

- 注入的根因是数据与语法混在一起，不是「特殊字符没过滤」。
- 转义依赖太多前提，无法作为长期防线。
- 数值参数、排序字段、表名同样是注入面。
